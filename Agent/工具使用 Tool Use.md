# 工具使用 Tool Use

> 标签：#概念/Agent #工具 #Tool-Use #函数调用 #Function-Calling

## 1. 工具为什么关键

LLM 原生只会「生成文本」。一旦能**调用外部工具**，能力边界被彻底打开：

- 算数、实时天气、数据库查询
- 写文件、跑代码、操作 shell
- 调用第三方 API、发消息、操控浏览器

工具使用是 Agent 从「聊天」走向「办事」的开关，也是 [[增强型LLM（检索-工具-记忆）]] 的三大支柱之一。

## 2. 函数调用（Function Calling）

现代 LLM 普遍支持结构化工具调用：

1. 开发者声明工具清单（名称、描述、JSON Schema 参数）
2. 模型输出结构化调用（如 `{"name":"search","arguments":{...}}`）
3. 运行时解析并执行，把结果回灌给模型

> 注意：模型输出的是「调用意图」，真正执行由宿主程序负责（安全第一）。

## 3. 代表性方法（Lil'Log 综述）

| 方法 | 思路 |
|------|------|
| **MRKL** | 模块化推理、知识与语言：LLM 当路由器，把请求分发给神经/符号专家模块（计算器、天气 API 等） |
| **TALM / Toolformer** | 微调语言模型，使其**自主学会**调用外部 API |
| **HuggingGPT** | 以 ChatGPT 为规划器：解析任务 → 筛选 HuggingFace 模型 → 执行 → 汇总（四阶段） |
| **API-Bank** | 含 53 个常用 API 的基准，评估「是否调用 / 检索正确 API / 多步规划调用」三级能力 |

## 4. 工具设计的原则

工具接口质量直接决定 Agent 成败（详见 [[构建最佳实践#3. 精心制作 Agent-计算机接口 ACI]]）：

- 工具描述要像写 prompt 一样精心
- 参数格式靠近模型「天然见过」的文本，避免让它手写 diff 行号、JSON 转义等
- 用「防错设计（poka-yoke）」：例如强制绝对路径，避免相对路径错误（参见 [[docker-compose 路径错位导致 make up 失败]] 的踩坑）

## 5. 风险

- 工具执行可能有副作用（删文件、发消息）→ 必须有权限隔离与人工确认
- 模型可能「幻觉」出不存在的工具或错误参数 → 需校验与降级
