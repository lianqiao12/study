# 构建最佳实践

> 标签：#概念/Agent #最佳实践 #ACI #Guardrails #工程

> 主要依据 Anthropic《Building Effective Agents》及业界共识。

## 1. 三大核心原则

1. **保持设计简单（Maintain simplicity）**：别一上来就堆复杂系统。从简单 prompt 开始，用评估验证，只有简单方案真的不够时才上多步代理。
2. **优先透明度（Prioritize transparency）**：显式展示 Agent 的规划步骤、调用了哪些工具、为什么这么做。让用户能看懂、能信任、能干预。
3. **精心制作 Agent-计算机接口 ACI（Agent-Computer Interface）**：把工具设计当成「人机界面（HCI）」来对待——这是成败关键。

## 2. 渐进式复杂度

```text
简单 prompt
   │ 评估不足？
   ▼
+ 检索/工具（增强型 LLM）
   │ 仍不足？
   ▼
+ Workflow 模式（链/路由/并行…）
   │ 路径仍无法写死？
   ▼
+ 自主 Agent
```

> 代理系统用「延迟 + 成本」换「性能」，复杂度越高代价越大。

## 3. 精心制作 Agent-计算机接口 ACI

工具是 Agent 与世界交互的唯一通道，工具质量 ≈ Agent 质量：

- **像写提示一样写工具定义**：名称、描述、参数说明要清晰、带示例、覆盖边界情况
- **格式贴合模型习惯**：避免让模型手写 diff 行号、JSON 转义等易错格式
- **防错设计（poka-yoke）**：例如强制绝对路径，避免相对路径错误——参见真实踩坑 [[docker-compose 路径错位导致 make up 失败]]
- **测试模型误用**：故意喂异常输入，看模型是否会错用工具
- 经验谈：在 SWE-bench Agent 中，优化工具花费的精力**多于**优化总体提示，且收益显著

## 4. 护栏（Guardrails）

- **权限最小化**：工具能读不能写、能沙箱不能直连生产
- **人工 checkpoint**：在关键/不可逆操作前暂停等人确认
- **输入/输出校验**：防注入（prompt injection）、防越权
- **预算与早停**：限制最大步数、最大 token，防止失控循环

## 5. 可观测性

- 全程 **Tracing**（各 SDK 均内置）：记录每一步 thought / action / observation
- 便于复盘失败、定位是「规划错」还是「工具错」还是「检索错」
- 与 [[增强型LLM（检索-工具-记忆）]] 的可透明度原则一致

## 6. 一句话总结

> 成功不在于构建最复杂的系统，而在于构建**最契合需求**的系统：以简单增强型 LLM 为基，按需组合模式，在开放场景中谨慎引入自主 Agent，始终坚持简单、透明、严谨的接口设计。
